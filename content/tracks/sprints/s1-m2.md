**About 3 to 4 hours, over two or three Sprint sessions.** Target: Nov 6. Same wiring as 1.1. You'll wake the chip, configure it, read all seven measurements in one burst, and stream them as CSV text at a steady 100 Hz.

## Goal, and why it matters

Turn the MPU-6050 from "answers its name" into "a sensor that streams data you can trust": every sample from the same instant, on a fixed 10 ms schedule, in a format a Python program can parse.

Three interview topics live in this milestone: **register configuration from a datasheet** (bit fields), **two's complement and endianness** (combining a high and a low byte into a signed 16-bit value), and **timing budgets** (will 100 Hz actually fit through a 115200-baud link?). Being able to do that timing math out loud is what separates "I used an Arduino" from "I designed firmware."

## Step 1: wake the chip

The MPU-6050 **powers up asleep**. Until you clear the sleep bit, every data register reads 0 (but `WHO_AM_I` still works, which is why 1.1 succeeded without this step).

`PWR_MGMT_1`, register `0x6B` (107). Reset value: **`0x40`**.

| Bit | 7 | 6 | 5 | 4 | 3 | 2:0 |
|---|---|---|---|---|---|---|
| Name | `DEVICE_RESET` | `SLEEP` | `CYCLE` | (reserved) | `TEMP_DIS` | `CLKSEL` |
| Meaning | 1 = reset all registers to defaults (self-clears) | 1 = sleep | 1 = cycle between sleep and one sample | | 1 = temperature sensor off | clock source |

`CLKSEL` values: `0` = internal 8 MHz oscillator, `1` = PLL using the X-axis gyro as reference, `2` and `3` = PLL with the Y or Z gyro, `4` and `5` = external clocks, `7` = stop the clock. The datasheet **recommends a gyro PLL** (1, 2, or 3) because it's more stable than the internal oscillator.

So: work out the byte that has `SLEEP` = 0, `CYCLE` = 0, `TEMP_DIS` = 0 (you want temperature), and `CLKSEL` set to the X-gyro PLL. Write it, wait a few milliseconds for the PLL to settle, then read the register back and check it.

You'll need a write function. Same shape as your read:

```c
// Writes one byte to register reg of I2C device dev. Returns 0 on success, else the Wire status.
uint8_t writeRegister(uint8_t dev, uint8_t reg, uint8_t value);
```

A register write is one transaction: START, address + W, register, value, STOP. So this one *does* end with a normal STOP.

## Step 2: configure the ranges and the filter

After reset, all of these registers are 0. That gives the ranges this course uses (±2 g and ±250 °/s), but write them explicitly anyway: a firmware that depends on reset defaults breaks the day someone else's code changes them first.

**`GYRO_CONFIG`, register `0x1B`.** `FS_SEL` is in **bits 4:3** (bits 7:5 are self-test, keep them 0).

| `FS_SEL` | Range | Sensitivity |
|---|---|---|
| 0 | ±250 °/s | **131** LSB per °/s |
| 1 | ±500 °/s | 65.5 LSB per °/s |
| 2 | ±1000 °/s | 32.8 LSB per °/s |
| 3 | ±2000 °/s | 16.4 LSB per °/s |

**`ACCEL_CONFIG`, register `0x1C`.** `AFS_SEL` is in **bits 4:3** (bits 7:5 are self-test).

| `AFS_SEL` | Range | Sensitivity |
|---|---|---|
| 0 | ±2 g | **16384** LSB per g |
| 1 | ±4 g | 8192 LSB per g |
| 2 | ±8 g | 4096 LSB per g |
| 3 | ±16 g | 2048 LSB per g |

Bit fields in bits 4:3 mean the value is shifted left by 3: `FS_SEL = 1` is the byte `0b00001000` = `0x08`, not `0x01`. Writing `0x01` instead sets a reserved bit and silently leaves the range at ±250 °/s. This exact mistake is a classic, and it's why you read every register back.

**`CONFIG`, register `0x1A`.** `DLPF_CFG` is in **bits 2:0**: the on-chip digital low-pass filter.

| `DLPF_CFG` | Accel bandwidth | Gyro bandwidth | Gyro delay | Gyro output rate |
|---|---|---|---|---|
| 0 | 260 Hz | 256 Hz | 0.98 ms | 8 kHz |
| 1 | 184 Hz | 188 Hz | 1.9 ms | 1 kHz |
| 2 | 94 Hz | 98 Hz | 2.8 ms | 1 kHz |
| 3 | 44 Hz | 42 Hz | 4.8 ms | 1 kHz |
| 4 | 21 Hz | 20 Hz | 8.3 ms | 1 kHz |
| 5 | 10 Hz | 10 Hz | 13.4 ms | 1 kHz |
| 6 | 5 Hz | 5 Hz | 18.6 ms | 1 kHz |

**Why this matters (signals, not software):** you will *sample* at 100 Hz, so the Nyquist frequency is 50 Hz. Any vibration above 50 Hz that reaches your samples **aliases** down into a fake low-frequency signal, and no amount of Python afterwards can remove it. The DLPF is your anti-aliasing filter, exactly like the RC filter in front of an ADC. Pick a setting whose bandwidth is below 50 Hz, and write down the trade-off you made (more filtering = more delay). Note that `DLPF_CFG` 0 or 7 turns the filter off.

**`SMPLRT_DIV`, register `0x19`.** Sample rate = gyro output rate / (1 + `SMPLRT_DIV`). With the DLPF on, the gyro output rate is 1 kHz.

Here's a subtle design choice. You could set the chip's internal rate to exactly 100 Hz (divider 9) to match your loop. But the chip's clock and the Uno's `millis()` are two different crystals that drift relative to each other, so every so often you'd read the same sample twice or skip one: a "beat" between two clocks. Leaving the internal rate at 1 kHz (divider 0) means each 10 ms read gets a sample that's at most 1 ms old. Pick one, and say why in your README. (The fully synchronized answer is the `INT` pin's data-ready interrupt: a good stretch goal.)

Print every configuration register back at startup as comment lines, for example `# CONFIG=0x03`. Comment lines start with `#` so your Python parser can skip them.

## Step 3: burst-read 14 bytes

The measurement registers sit next to each other, **high byte first** (big-endian):

| Register | Name | Register | Name |
|---|---|---|---|
| `0x3B` | `ACCEL_XOUT_H` | `0x3C` | `ACCEL_XOUT_L` |
| `0x3D` | `ACCEL_YOUT_H` | `0x3E` | `ACCEL_YOUT_L` |
| `0x3F` | `ACCEL_ZOUT_H` | `0x40` | `ACCEL_ZOUT_L` |
| `0x41` | `TEMP_OUT_H` | `0x42` | `TEMP_OUT_L` |
| `0x43` | `GYRO_XOUT_H` | `0x44` | `GYRO_XOUT_L` |
| `0x45` | `GYRO_YOUT_H` | `0x46` | `GYRO_YOUT_L` |
| `0x47` | `GYRO_ZOUT_H` | `0x48` | `GYRO_ZOUT_L` |

The chip **auto-increments** its register pointer during a read, so one transaction (write `0x3B`, repeated START, read 14 bytes) returns all 14 in that order.

**Why a burst and not 14 single reads?** The register map explains that the readable registers are a copy of the internal ones, refreshed only while the I2C interface is idle. A burst read therefore gets all seven values **from the same sampling instant**. Fourteen separate reads could mix the high byte of one sample with the low byte of the next: a glitch that shows up as a jump of about 256 counts, once in a while, impossible to reproduce. That's a great interview story *because* it's so hard to debug.

The `Wire` receive buffer on the Uno is 32 bytes, so 14 fits in one `requestFrom`.

Function signature:

```c
// Reads n consecutive registers starting at start into buf[0..n-1].
// Returns 0 on success, else an error code (and buf contents are not valid).
uint8_t readRegisters(uint8_t dev, uint8_t start, uint8_t *buf, uint8_t n);
```

## Step 4: combine high and low bytes into `int16_t`

Each measurement is a 16-bit **two's complement** number split across two bytes: `0x3B` holds bits 15:8 and `0x3C` holds bits 7:0. Your job: build the 16-bit pattern from the two bytes, then interpret it as signed.

Worked examples (do these on paper first):

| High byte | Low byte | 16-bit pattern | As `int16_t` |
|---|---|---|---|
| `0x40` | `0x00` | `0x4000` | +16384 (1 g at ±2 g) |
| `0x00` | `0x83` | `0x0083` | +131 (1 °/s at ±250 °/s) |
| `0xFF` | `0x7D` | `0xFF7D` | -131 |
| `0xC0` | `0x00` | `0xC000` | -16384 (-1 g) |
| `0x80` | `0x00` | `0x8000` | -32768 (most negative) |

Things to get right in C on the AVR:

- A `uint8_t` used in arithmetic is **promoted to `int`**, which is 16 bits on the Uno. Shifting `0xFF` left by 8 as a signed 16-bit `int` overflows the signed range, which is undefined behavior in C. Do the shift on an **unsigned 16-bit** type, combine with OR, and only then convert the finished bit pattern to `int16_t`.
- If you store the result in a `uint16_t` or an `unsigned int` and print it, -131 shows up as 65405. That's the signed-vs-unsigned bug; your Python tests in 1.3 check for it too.
- If you swap which byte is high and which is low, small values look huge (1 becomes 256). That's the endianness bug.

## Step 5: stream on a fixed 100 Hz schedule

### The CSV stream format (this is a spec: 1.3 depends on it)

- Baud rate **115200**, 8N1.
- At startup: any number of comment lines starting with `#` (your config read-backs, a version string), then one header line, exactly:

```
t_ms,ax,ay,az,temp,gx,gy,gz
```

- Then one data line per sample: **8 integers, comma-separated, no spaces**, ending with `\r\n` (that's what `Serial.println` sends). `t_ms` is `millis()` at the moment of the read; the other seven are the raw signed counts in register order. Example:

```
123450,312,-88,16290,-1544,-21,13,-6
```

- Errors are comment lines: `# ERROR burst read failed, status 2`.

### Timing: do the math first

At 100 Hz you have a **10 ms** budget per sample. What does each part cost?

**I2C, 14-byte burst at the default 100 kHz clock.** Each byte on the bus is 9 clock cycles (8 data bits + ACK). The transaction is: START, address+W, register, repeated START, address+R, 14 data bytes, STOP. That's about 1 + 9 + 9 + 1 + 9 + 14 × 9 + 1 ≈ 156 clock cycles ≈ **1.6 ms**. At 400 kHz (`Wire.setClock(400000)`; the MPU-6050 supports fast mode) it's about **0.4 ms**.

**Serial.** 115200 baud with 8N1 framing is 10 bits per byte on the wire, so about 11,520 bytes/s, or **87 µs per byte**. The longest possible line is `4294967295,-32768,-32768,-32768,-32768,-32768,-32768,-32768\r\n`: 10 + 7 × 7 + 2 = **61 bytes**, or about **5.3 ms**. A typical line (about 40 bytes) takes about 3.5 ms.

**The serial buffer.** `Serial.print` copies bytes into a **64-byte** transmit buffer and returns; an interrupt drains it in the background. As long as a whole line fits in the buffer and the previous line has finished draining before the next one starts, printing costs you almost nothing. If you print faster than the line can drain, `Serial.print` **blocks** until there's room, and your loop silently slows down.

Now redo the serial math at **9600 baud**: 61 bytes take about 64 ms. A 100 Hz stream is impossible, and nothing errors: you just get about 16 Hz. That's why the baud rate is part of the spec.

Write your own version of this budget in your README: I2C time + serial time + slack, at the I2C clock and baud you chose.

### The `millis()` schedule

`delay(10)` is wrong here: the loop period becomes 10 ms **plus** the time your code takes, so you'd get about 90 Hz, drifting with whatever you print. Instead, keep the time of the next deadline and only do the work when `millis()` reaches it.

Two details turn a beginner scheduler into a professional one:

1. **Advance the deadline by exactly one period**, not to "now plus one period." If one loop runs 2 ms late, the next deadline is still on the 10 ms grid, so the long-run rate stays exactly 100 Hz and errors don't accumulate.
2. **Compare with unsigned subtraction** (`now - last` as `unsigned long`), not `now >= next`. `millis()` wraps to 0 after about 49.7 days; unsigned subtraction gives the right answer across the wrap, and a direct comparison doesn't. Interviewers love this one.

Optionally count overruns (times you were more than a full period late) and print the count in a comment line every few seconds. It's cheap insurance, like a scan-time alarm on a PLC.

<details><summary>Hint 3 (pseudocode)</summary>

```
setup:
    serial at 115200, start the I2C bus
    write PWR_MGMT_1 = (byte with SLEEP clear and CLKSEL = X-gyro PLL)
    wait 10 ms; read PWR_MGMT_1 back; print "# PWR_MGMT_1=0x.."
    for each of CONFIG, SMPLRT_DIV, GYRO_CONFIG, ACCEL_CONFIG:
        write your value; read it back; print "# NAME=0x.."
    print the header line
    last = millis()

loop:
    now = millis()
    if (now - last) < 10: return            (unsigned subtraction)
    last = last + 10                        (stay on the grid)
    status = readRegisters(0x68, 0x3B, buf, 14)
    if status != 0: print "# ERROR burst read failed, status " status; return
    print now
    for k from 0 to 6:
        pattern = (high byte buf[2k], as unsigned 16-bit, shifted left 8) OR low byte buf[2k+1]
        value = pattern reinterpreted as a signed 16-bit integer
        print "," then value
    end the line
```

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| All seven values are 0 | Chip still asleep (the `SLEEP` bit is set) | Check your `PWR_MGMT_1` write status and the read-back. |
| Values never change, even when you shake it | Asleep again after a reset, or `CYCLE` mode, or you print the same buffer every time | Read back `PWR_MGMT_1`; make sure each loop does a fresh read. |
| `az` is about 8192 flat on the desk | `ACCEL_CONFIG` set to ±4 g (wrong bit position) | `AFS_SEL` is bits 4:3. Print the read-back. |
| Small tilts give jumps of about 256 | High and low bytes swapped | `0x3B` is the **high** byte. |
| Negative values print as 65000-something | Stored or printed as unsigned | Keep the final value in an `int16_t`. |
| Occasional single-sample spikes of about ±256 | Reading registers one at a time instead of a burst | Use one 14-byte burst read. |
| Rate below 100 Hz, and lines arrive in clumps | Baud set too low, extra debug prints, or `delay()` in the loop | 115200 baud, no `delay()`, only the CSV line per sample. |
| Garbage characters in the monitor | Monitor baud doesn't match `Serial.begin` | Set the monitor to 115200. |
| The stream restarts (header appears again) when you open the monitor | That's normal: opening the port toggles DTR, which resets the Uno | Your Python logger in 1.3 must expect this. |
| Sketch freezes forever when you unplug SDA | The I2C transaction hangs waiting for the bus | Use `Wire.setWireTimeout(...)` in `setup()` so a stuck bus returns an error (status 5) instead of hanging. |
| Temperature converts to about 36 °C at room temperature | You converted a 0 (chip asleep), or used the wrong formula for a clone | Check the raw value isn't 0. Clones (`WHO_AM_I` 0x70/0x72) use a different formula. |
