## Step 1: organize the repo for testing

Move the tests out of `host/` into their own folder, and tell pytest where your code lives:

```
imu-pipeline/
  host/            your modules (no tests in here any more)
  tests/
    site/          the course's test files, unchanged (credit the course in a comment)
    test_convert_mine.py
    test_packet_mine.py
    test_logger_mine.py
  data/
    capture_clean_10s.bin
  pytest.ini
  requirements.txt
```

`pytest.ini` at the repo root:

```ini
[pytest]
testpaths = tests
pythonpath = host
markers =
    hardware: needs the Uno plugged in (skipped in CI)
```

`pythonpath = host` puts your `host/` folder on the import path, so `from imu_packet import PacketParser` works from any test. `testpaths` tells pytest where to look when you just type `python -m pytest`.

`requirements.txt`, pinned to the versions in your conda env (check yours with `python -m pip list`):

```
numpy==2.4.6
matplotlib==3.11.2
pyserial==3.5
pytest==9.1.1
```

Pinning means CI tests exactly what you ran. If a version doesn't exist on PyPI for the CI runner, loosen it to `>=` the major version and note why.

## Step 2: decide what to test

A good suite isn't "many tests"; it's tests chosen to catch the bugs that would actually happen. Use these four kinds, and write the test **name and docstring before the body**: if you can't say what it proves in one line, it isn't a test yet.

| Kind | What it means | Examples for your pipeline (write your own versions) |
|---|---|---|
| **Normal** | typical input, typical answer | a clean CSV line; a clean stream of 100 frames; 1 g at 16384 counts |
| **Edge** | the boundaries | `int16` extremes -32768 and 32767; `seq` wrapping 255 to 0; `t_ms` at 2^32 - 1; an empty `feed(b"")`; exactly one frame |
| **Bad input** | input your code must reject, without crashing | a header line; `1.5` in a field; a frame of 22 bytes; `feed("text")` |
| **Fault injection** | deliberately damaged data, like a noisy cable | one flipped bit; a truncated frame; random garbage between frames; a sync pattern inside the payload; a burst of 300 lost frames (what does your `dropped` count say? is that a limitation worth documenting?) |

Fault-injection tests use **seeded** randomness (`random.Random(1234)` or `np.random.default_rng(1234)`), so a failure is reproducible. A test that fails one run in fifty is worse than no test.

**`parametrize`** is how you test ten bad lines without writing ten functions: one test body, a list of inputs, and pytest reports each one separately. Look it up in the pytest docs ("How to parametrize fixtures and test functions").

## Step 3: a recorded capture as a fixture

Synthetic data proves your parser against *your* understanding of the protocol. A **recording from the real device** proves it against reality. Capture 10 s of raw bytes from your Uno to a file (a short script that opens the port, reads for 10 s, and writes the bytes with `open(path, "wb")`). Commit it (10 s × 2300 bytes/s ≈ 23 kB is fine).

Then write tests that replay it:

- the whole file in one `feed` gives about 1000 samples, with `corrupt == 0`
- the same file fed in random chunk sizes gives the same samples
- the same file with seeded bit flips loses only the damaged frames

Load the file in a **fixture** (a function decorated with `@pytest.fixture` that returns the bytes), so each test just asks for it by name.

## Step 4: make the logger testable

Your logger currently mixes three jobs: talking to the serial port, parsing, and writing files. Only the first one needs hardware. Pull the file writing out into a function, for example:

```python
def write_samples(path, samples):
    """Write samples (tuples of 8 ints, plus host time) to a CSV log with a header row."""
```

Now a test can call it with a `tmp_path` file (pytest gives each test a fresh temporary folder) and read the file back to check the header, the row count, and that nothing got a blank line between rows on Windows.

The same idea scales up: a **fake serial port** (a tiny class with a `read(n)` method that returns bytes from a list you prepare) lets you test the whole logger loop with no hardware at all. That technique is called dependency injection, and it's exactly how hardware-in-the-loop test rigs are built. Mention it in interviews.

Tests that really need the Uno get `@pytest.mark.hardware`. In CI, run `python -m pytest -m "not hardware"` so they're skipped.

## Step 5: GitHub Actions

A workflow is a YAML file in `.github/workflows/`. GitHub reads it on every push and runs the jobs on a fresh virtual machine. Your workflow needs these parts (look up each in GitHub's docs, "Building and testing Python"):

| Key | What it does |
|---|---|
| `name:` | the workflow's name in the Actions tab and on the badge |
| `on:` | which events trigger it: you want `push` and `pull_request` |
| `jobs:` → a job id → `runs-on:` | the machine: `ubuntu-latest` (cheapest and fastest; your code isn't Windows-specific) |
| `steps:` | in order: check out the repo, set up Python 3.11, install `requirements.txt`, run pytest without the hardware tests |
| `uses: actions/checkout@v4` | the step that copies your repo onto the runner |
| `uses: actions/setup-python@v5` with `python-version: "3.11"` | the step that installs Python, matching your conda env |
| `run:` | a shell command, like `python -m pip install -r requirements.txt` |

If any test imports `matplotlib.pyplot`, set the environment variable `MPLBACKEND: Agg` for the test step: the runner has no screen.

Push, then open your repo on GitHub > **Actions** to watch it run. Click into a failed run to see pytest's output, exactly as you'd see it locally.

**The badge.** In the Actions tab, open your workflow, click "..." > "Create status badge", and paste the Markdown into the top of your README. It looks like `![tests](https://github.com/<your-user>/imu-pipeline/actions/workflows/tests.yml/badge.svg)`.

## Common beginner mistakes

- Tests that test nothing: `assert parse_csv_line(line)` passes for any non-empty tuple, including the wrong one. Assert the exact value.
- Testing only the happy path. A parser's job is the unhappy path.
- Unseeded randomness, so CI is red one day and green the next.
- Tests that depend on each other (one test's output is the next test's input). Each test must run alone.
- Floating-point equality with `==`. Use `pytest.approx`.
- Running CI on `windows-latest` "to match the laptop": it's slower and nothing here is Windows-specific.
- Committing `__pycache__/` and `.pytest_cache/`. Add them to `.gitignore`.

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| `ModuleNotFoundError: No module named 'imu_packet'` | `pythonpath = host` missing, or pytest started from the wrong folder | Run from the repo root; check `pytest.ini`. |
| Works locally, fails in CI with `ModuleNotFoundError: serial` | `pyserial` missing from `requirements.txt` | Add it (the package is `pyserial`; the import is `serial`). |
| CI fails with a version that doesn't exist | A pin that only exists for conda, or only for Windows | Loosen that pin to a range. |
| CI hangs | A test tries to open a COM port | Mark it `hardware` and exclude it in CI. |
| The workflow never runs | File not under `.github/workflows/`, or a YAML indentation error | Check the Actions tab for a parse error; fix indentation. |
| `_tkinter.TclError: no display` | `pyplot` tried to open a window on the runner | Set `MPLBACKEND: Agg`. |
| A test passes alone but fails in the full run | Tests share state (a module-level list, a file in the repo) | Use fixtures and `tmp_path`; never write into the repo from a test. |
