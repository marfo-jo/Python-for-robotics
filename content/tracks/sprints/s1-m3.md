## Part 1: `imu_convert.py`, the spec

This module turns one line of text into numbers and numbers into physical units. It's pure computation (no serial port, no files), which is why it's easy to test. Write it in your repo at `host/imu_convert.py`. Your names and signatures must match exactly, because the tests import them.

### Constants

```python
ACCEL_LSB_PER_G = 16384.0    # at +-2 g  (ACCEL_CONFIG AFS_SEL = 0)
GYRO_LSB_PER_DPS = 131.0     # at +-250 deg/s  (GYRO_CONFIG FS_SEL = 0)
```

### `combine_bytes(hi, lo) -> int`

Combine a **high byte** and a **low byte** (each an `int` from 0 to 255, in the order the MPU-6050 sends them: `0x3B` is high, `0x3C` is low) into a **signed 16-bit** value from -32768 to 32767. It's the Python mirror of what your firmware does in C, and it'll come back in 1.4.

- `combine_bytes(0x40, 0x00)` returns `16384`; `combine_bytes(0xFF, 0xFF)` returns `-1`; `combine_bytes(0x80, 0x00)` returns `-32768`.
- Raise `ValueError` if either argument isn't an `int` in 0..255 (for example `256`, `-1`, or `1.5`).

Python integers never overflow, so there's no "free" sign bit: if the combined 16-bit pattern is 0x8000 or more, *you* have to turn it into the negative number it represents. Work out the rule from the two's complement table in 1.2.

### `parse_csv_line(line) -> tuple or None`

Parse one line of the 1.2 stream format.

- `line` is a `str` **or** `bytes` (pyserial's `readline()` gives you `bytes` like `b'123450,312,-88,16290,-1544,-21,13,-6\r\n'`). Decode `bytes` as ASCII.
- Strip surrounding whitespace, including the `\r\n`.
- For a valid data line, return a **tuple of 8 `int`s**: `(t_ms, ax, ay, az, temp, gx, gy, gz)`.
- Return **`None`** (never raise) for anything that isn't a valid data line:
  - an empty line, or a comment line starting with `#`
  - the header line `t_ms,ax,ay,az,temp,gx,gy,gz`
  - the wrong number of fields (the first line after opening the port is often cut in half)
  - any field that isn't an integer (`abc`, `1.5`, or an empty field from `1,2,,4`)
  - bytes that can't be decoded (what you get at the wrong baud rate)
  - a sensor field outside -32768..32767, or a negative `t_ms`

**Why return `None` instead of raising?** Because on a live serial link, bad lines are *expected*, not exceptional. The logger's job is to count them and keep going. A parser that crashes the logger on the first noisy byte is a bug, and an interviewer will ask you about this choice.

### `raw_to_g(raw, lsb_per_g=ACCEL_LSB_PER_G) -> float`
### `raw_to_dps(raw, lsb_per_dps=GYRO_LSB_PER_DPS) -> float`

Divide by the sensitivity. The keyword argument lets you pass another range's sensitivity (4096 for ±8 g, 16.4 for ±2000 °/s). Both must also work when `raw` is a **numpy array** (convert a whole column in one call); plain division already does, as long as you don't loop or call `int()`/`float()` on it.

### `raw_to_celsius(raw) -> float`

The datasheet formula: temperature in °C = raw / 340 + 36.53.

## Part 2: `log_serial.py`, the logger

This is a script, not a module with a spec, so the tests don't check it. You check it with real data. Requirements:

1. **Command-line options** with `argparse`: `--port` (for example `COM3`), `--baud` (default 115200), `--seconds` (default 60), and `--out` (default: a timestamped name like `data/imu_20261108_141502.csv`, so you never overwrite a log).
2. **Open the port, then expect a reset.** Opening the port toggles DTR, which resets the Uno; you'll get about 2 s of nothing, then the `#` comment lines and the header. Clear anything stale in the input buffer, and use a read timeout so the script can't hang forever.
3. **Read line by line.** Pass every line to `parse_csv_line`. Count `None` results as rejected (but don't count `#` comments and the header as errors: track those separately, or just skip them before parsing). Print every `# ERROR` line from the firmware to the terminal so you see bus problems live.
4. **Write the log** with the `csv` module: a header row, then one row per good sample. Log the **raw integers** plus the host's receive time. Store raw, convert later: if you ever discover your scale factor was wrong, raw data can be re-converted and converted data can't.

   Suggested columns: `host_time_s,t_ms,ax,ay,az,temp,gx,gy,gz`.
5. **Stop cleanly** after `--seconds`, or on Ctrl+C (`KeyboardInterrupt`), and always close the file and the port (use `with` blocks).
6. **Print a summary**: good lines, rejected lines, duration, and the rate computed from the Uno's `t_ms` (number of samples divided by elapsed `t_ms`). Also count **gaps**: consecutive `t_ms` values that differ by more than 10 ms.

Run it:

```powershell
conda activate robotics-course
cd C:\path\to\imu-pipeline
python host\log_serial.py --port COM3 --seconds 60
```

**Close the Arduino Serial Monitor first.** Only one program can own a COM port on Windows.

## Common beginner mistakes

- `parse_csv_line` crashes on the header line because `int("t_ms")` raises. Catch `ValueError` and return `None`.
- Checking for a blank line *before* stripping. A "blank" line from the serial port is really `"\r\n"`, so `line == ""` is false and it gets counted as a corrupt line instead of skipped. Strip first, then test.
- Treating the combined 16-bit value as unsigned: -1 shows up as 65535.
- Reading with `ser.read()` (one byte) in a loop instead of `readline()`, and building lines by hand without a reason.
- Writing the CSV with `open(path, "w")` on Windows and getting a blank line between every row. Use `newline=""`.
- Never closing the file. If the script crashes, the last few seconds are lost in a buffer.
- Plotting `t_ms` on the x-axis and labeling it "seconds."

<details><summary>Hint 2 (approach): parse_csv_line and combine_bytes</summary>

`parse_csv_line`: if it's bytes, try to decode it (catch the decode error and return `None`). Strip. Reject empty and `#` lines. Split on commas; reject if the count isn't 8. Convert every field with `int()` inside one `try`; on `ValueError` return `None`. Check `t_ms` and the seven ranges. Return `tuple(...)`.

`combine_bytes`: validate both arguments first. Build the 16-bit pattern with a shift and an OR. If the pattern is at least 0x8000, subtract 0x10000 (that's 65536: one full turn of a 16-bit counter).

</details>

<details><summary>Hint 3 (pseudocode): the logger loop</summary>

```
parse the command-line arguments
open the serial port with a 1 s timeout              (with-block)
wait about 2 s for the board to reset, then clear the input buffer
open the output file with newline=""                 (with-block)
write the header row
start = now; good = rejected = gaps = 0; last_t = None
while now - start < seconds:
    raw = read one line (bytes; empty if the timeout expired)
    if raw is empty: continue
    if it starts with "#": print it if it contains ERROR; continue
    sample = parse_csv_line(raw)
    if sample is None: rejected += 1; continue
    if last_t is not None and sample t_ms - last_t > 10: gaps += 1
    last_t = sample t_ms
    write a row: host time, then the 8 values
    good += 1
print good, rejected, gaps, and the rate from the first and last t_ms
(Ctrl+C: catch KeyboardInterrupt around the loop so the summary still prints)
```

</details>

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| `SerialException: could not open port 'COM3': PermissionError(13, 'Access is denied.')` | The Arduino Serial Monitor (or another script) has the port open | Close it. Only one program can own a COM port. |
| `could not open port 'COM3': FileNotFoundError` | Wrong port name, or the Uno is unplugged | `python -m serial.tools.list_ports -v` lists ports and their descriptions. |
| Nothing for the first 2 s, then data | Opening the port reset the Uno (DTR) | Normal. Wait, then clear the input buffer. |
| `readline()` returns `b''` | The read timeout expired with no newline | Firmware not running, wrong port, or wrong baud. Check in Serial Monitor first (then close it). |
| `UnicodeDecodeError`, or lines full of junk | Baud mismatch between Python and the firmware | Both must be 115200. Your parser should return `None` for these, not crash. |
| One bad line at the very start | You opened the port mid-line | Expected; it's why the parser rejects bad field counts. |
| Bursts of rejected lines when you bump the USB cable | Loose USB connection or a cheap cable | Try another cable and USB port. |
| Rate well below 100 Hz, `t_ms` steps of 10 but gaps | The script is too slow (printing every line to the terminal) and the OS buffer overflowed | Don't print every sample. Print a status line once a second. |
| CSV has a blank line after every row | Opened without `newline=""` on Windows | `open(path, "w", newline="")`. |
| Log file is empty or cut short after a crash | File not closed or flushed | Use `with open(...)`, and flush once a second. |
| `t_ms` suddenly jumps back to a small number mid-log | The Uno reset (brown-out, or the port was reopened) | Look for a second header line in the raw stream; your logger can count resets. |
| `ModuleNotFoundError: No module named 'imu_convert'` when running pytest | The test file isn't next to your module, or you're in the wrong folder | `cd host` first, or set `PYTHONPATH` (see Part 1). |
| `ModuleNotFoundError: No module named 'serial'` | Wrong Python: not the conda env | `conda activate robotics-course`. In VS Code, pick that interpreter (Ctrl+Shift+P > Python: Select Interpreter). |

## Resume and interview note

The minimal version is a real project: link it in applications now. Be ready to answer:

- "How does your parser handle a corrupted line?" (it returns `None`, the logger counts it, and the rate and gap counts tell you how healthy the link is)
