**About 2 to 3 hours, over two Sprint sessions.** Target: Nov 2. You'll wire the GY-521, prove the bus works with a diagnostic scanner, then write your first register read in C.

## Goal, and why it matters

Read the MPU-6050's `WHO_AM_I` register with **your own** I2C code and get `0x68` back.

That one byte proves the whole chain: power, ground, both I2C wires, the address, and your understanding of an I2C register read. It's the "hello world" of sensor bring-up, and it's exactly the first thing an embedded engineer does with a new board. In an interview, "how would you bring up a new I2C sensor?" has a textbook answer, and after today it's *your* answer: check power, scan the bus, read the identity register, then configure.

## Wiring

![Wiring diagram: Uno 5V to GY-521 VCC, GND to GND, A4 to SDA, A5 to SCL; XDA, XCL, AD0 and INT not connected](content/tracks/sprints/img/uno-gy521.svg)

| Uno pin | GY-521 pin | Wire color (suggested) | Why |
|---|---|---|---|
| 5V | VCC | red | The GY-521 has its own 3.3 V regulator, so it takes 5 V on VCC. |
| GND | GND | black | Common reference. Always wire ground first. |
| A4 (SDA) | SDA | blue | I2C data. On the Uno R3, A4 *is* SDA (the pin labeled SDA near AREF is the same signal). |
| A5 (SCL) | SCL | orange or yellow | I2C clock. Same story: A5 is SCL. |
| (none) | XDA, XCL | | Auxiliary I2C master bus for an external magnetometer. Leave open. |
| (none) | AD0 | | Address select. Pulled low on the board, so the address is **0x68**. Tie to 3.3 V for 0x69. |
| (none) | INT | | Data-ready interrupt output. Not needed yet. |

**Electrical notes (interview-grade, so read them):**

- I2C lines are **open-drain**: devices only pull the line low; resistors pull it high. The GY-521 has its pull-up resistors to its own **3.3 V**, so a logic 1 on the bus is about 3.3 V.
- The Uno is a 5 V part. Its input-high threshold is 0.6 × VCC = 3.0 V, so 3.3 V reads as HIGH, but with only about 0.3 V of margin. That's why **short wires (under 20 cm)** matter: long wires add capacitance, slow the rising edges, and eat that margin.
- The `Wire` library on the Uno also turns on the ATmega's weak internal pull-ups (tens of kΩ to 5 V). Against the module's much stronger pull-ups to 3.3 V, the bus idles at roughly 3.3 to 3.5 V. **Do not add your own external pull-ups to 5 V**: that would drive the MPU-6050's 3.3 V pins above their rating.

**Safety:** this is a 5 V circuit, so it can't hurt you, but you can hurt it. Unplug USB before moving any wire. Swapping VCC and GND for even a second can kill the module (that's why you bought a 3-pack).

## Step 1: check power before logic

1. With USB unplugged, wire only GND and VCC.
2. Plug in USB. The GY-521's power LED should light.
3. Multimeter on DC volts: VCC to GND should read about 5 V (4.7 to 5.1 V on USB power is normal).
4. Unplug, then add SDA and SCL.

This is the same order you'd use commissioning a PLC panel: confirm the supply before you blame the I/O.

## Step 2: prove the bus with the diagnostic scanner

The course repo has a **diagnostic tool** at `local/sprint1/tools/i2c_scanner/i2c_scanner.ino`. It's the I2C equivalent of a multimeter: it asks every address "is anyone there?" and lists who answers. It does not touch any MPU-6050 register, so it doesn't do your milestone work for you.

**Arduino IDE 2 on Windows:**

1. File > Open > `local\sprint1\tools\i2c_scanner\i2c_scanner.ino` (in the course repo).
2. Tools > Board > Arduino AVR Boards > **Arduino Uno**.
3. Tools > Port > pick the one that says **(Arduino Uno)**, for example `COM3`. If you're unsure which COM port it is, unplug the Uno, look at the list, plug it back in, and see which one appears. Device Manager > Ports (COM & LPT) shows the same thing.
4. Upload (the right-arrow button, or Ctrl+U). Wait for "Done uploading."
5. Tools > Serial Monitor (Ctrl+Shift+M). Set the baud dropdown (bottom right) to **115200**.

You should see:

```

found device at 0x68
scan done, devices: 1
```

## Step 3: understand an I2C register read

Most I2C sensors work like a tiny memory: a list of 8-bit registers, each with an address. To read one, you first **write** the register address you want (this sets the chip's internal register pointer), then **read** bytes starting from there.

On the wire, reading `WHO_AM_I` looks like this:

```
START | 0x68 + W | ACK | 0x75 | ACK | REPEATED START | 0x68 + R | ACK | data byte | NACK | STOP
        address        (register)                     address              (from the chip)
```

- The 7-bit address `0x68` is sent with a direction bit in bit 0: `0xD0` means write, `0xD1` means read. The `Wire` library adds that bit for you; you always pass `0x68`.
- **ACK** means "I'm here and I got that byte". A missing ACK after the address is how you know nobody answered.
- The **repeated START** keeps control of the bus between the write and the read, so nothing can sneak in and move the register pointer.
- The master ends the read with a **NACK** to say "that's the last byte I want."

### How that maps onto `Wire`

| Bus step | `Wire` call | What it returns |
|---|---|---|
| START, address + W | `Wire.beginTransmission(addr)` | nothing (it only queues) |
| register byte | `Wire.write(reg)` | number of bytes queued |
| send it, but repeated START instead of STOP | `Wire.endTransmission(false)` | **status**: 0 success, 1 data too long, 2 NACK on address, 3 NACK on data, 4 other error, 5 timeout |
| repeated START, address + R, read n bytes, NACK, STOP | `Wire.requestFrom(addr, n)` | number of bytes actually received |
| take each byte out of the receive buffer | `Wire.read()` | the byte |

Two things beginners skip, and both cause silent bugs:

1. **Check the status of `endTransmission`.** A 2 means the chip didn't answer its address. If you ignore it and read anyway, you get garbage that looks like data.
2. **Check what `requestFrom` returned.** If it got fewer bytes than you asked for, `Wire.read()` returns -1 (which prints as 0xFF in a byte). That's the famous "my sensor reads 0xFF" bug.

### The register

From the register map, section "Register 117: Who Am I":

| Register | Name | Bits | Meaning |
|---|---|---|---|
| `0x75` (117) | `WHO_AM_I` | [6:1] | upper 6 bits of the 7-bit I2C address; bits 7 and 0 are reserved |

The default value is **0x68**, and it stays 0x68 even if you tie AD0 high and the chip moves to address 0x69 (the register doesn't include the AD0 bit). This register is read-only and works even while the chip is asleep, which is why it's the first thing you read.

## Step 4: write `who_am_i.ino`

Create `firmware/who_am_i/who_am_i.ino` in **your** repo. (The folder name must match the sketch name, or the Arduino IDE will offer to move it.)

Design it as a reusable function now, because 1.2 needs the same thing for 14 bytes. A good C shape for "do I/O, report success or failure" is to **return a status and pass the result out through a pointer**:

```c
// Reads one 8-bit register from the I2C device at address dev.
// Returns 0 on success and puts the byte in *value.
// Returns a nonzero error code on failure and leaves *value unchanged.
uint8_t readRegister(uint8_t dev, uint8_t reg, uint8_t *value);
```

That's the signature. The body is yours. Your `setup()` starts `Serial` at 115200 and starts `Wire`; your `loop()` calls `readRegister` once per second and prints either the value or the error.

Print format (so your Python later can recognize it): a value line looks like `WHO_AM_I = 0x68`, and an error line starts with `ERROR`, for example `ERROR read 0x75 failed, status 2`. Print hex with a leading zero for values below 0x10 (`Serial.print(x, HEX)` alone prints `8`, not `08`).

Upload it with the same steps as the scanner, and open Serial Monitor at 115200.

### Common beginner mistakes

- Passing `0xD0` (the 8-bit "write address") to `Wire`. `Wire` wants the 7-bit address `0x68`.
- Calling `Wire.endTransmission()` with no argument between the write and the read. That sends a STOP instead of a repeated START. The MPU-6050 usually tolerates it, but many sensors don't, and it's wrong per the datasheet's timing diagrams.
- Forgetting `Wire.begin()` in `setup()`. Every transaction then fails.
- Reading with `Wire.read()` without checking `Wire.available()` or the `requestFrom` count.
- Printing with `Serial.println(value)` and seeing `104`. That's correct! 104 decimal is 0x68. Print in hex.

## Hints

<details><summary>Hint 1 (nudge)</summary>

A register read is two transactions glued together by a repeated START: first you *write* one byte (the register address), then you *read* one byte. Look at the `Wire` table above and pick the calls for each half. Every call that can fail gives you a number back: keep it.

</details>

<details><summary>Hint 2 (approach)</summary>

Inside `readRegister`: queue the register address for device `dev`; finish the write half **without** a STOP and keep its status; if the status isn't 0, return it. Then ask for exactly 1 byte; if you didn't receive exactly 1, return your own error code (pick a number that `Wire` doesn't use, like 10). Otherwise store the byte through the pointer and return 0. In `loop()`, declare a `uint8_t` and pass its address (`&who`).

</details>

<details><summary>Hint 3 (pseudocode)</summary>

```
function readRegister(dev, reg, value_ptr):
    start a transmission to dev
    queue the byte reg
    status = end the transmission, keeping the bus (repeated start)
    if status is not 0: return status
    count = request 1 byte from dev
    if count is not 1: return MY_SHORT_READ_ERROR
    store the received byte at value_ptr
    return 0

loop:
    status = readRegister(0x68, 0x75, address of who)
    if status is 0: print "WHO_AM_I = 0x" and who as two hex digits
    else: print "ERROR read 0x75 failed, status " and status
    wait one second
```

</details>

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| Scanner: `no devices found` | SDA/SCL swapped, a loose jumper, or no power to the module | Check the LED, then check A4 = SDA and A5 = SCL. Wiggle each wire. |
| Scanner hangs or prints `timeout` | SDA or SCL shorted to GND, or the module is dead | Unplug USB, check for solder bridges on the header, try a spare module. |
| Scanner finds `0x69` instead of `0x68` | AD0 is high (a bridge on AD0, or wired to VCC) | Leave AD0 unconnected, or use 0x69 in your code. |
| `WHO_AM_I = 0xFF` | Your code read when nothing was received (`Wire.read()` returned -1), or SDA is floating high | Check the `requestFrom` count, and check the SDA wire. |
| `WHO_AM_I = 0x00` | SDA held low, or you printed a variable you never filled (status was nonzero) | Print the status. Check SDA for a short to GND. |
| `WHO_AM_I = 0x70`, `0x72`, or `0x98` | Not a genuine MPU-6050 (an MPU-6500 or a clone). Common on cheap modules. | It mostly behaves like an MPU-6050 for accel and gyro, but the temperature formula differs. Note it in your README, or try another module from the pack. |
| Serial Monitor shows garbage like `⸮⸮⸮` | Baud mismatch | Set the monitor to 115200 to match `Serial.begin(115200)`. |
| Upload fails: `Access is denied` / `port busy` | Another program has the COM port open (a second Serial Monitor, a Python script, Cura, a 3D-printer tool) | Close it. Only one program can own a COM port on Windows. |
| Upload fails: `programmer is not responding` / `not in sync` | Wrong board or port selected, or something on D0/D1 | Re-select Board and Port. Nothing should be wired to D0/D1. |
| Works on the bench, fails when you move the wires | Long or flaky jumpers (rising edges too slow) | Use short jumpers, under 20 cm. Push the module firmly into the breadboard. |

## Resume and interview note

You can now say, truthfully: "I brought up an MPU-6050 over I2C from the datasheet, with no device library." Be ready for these follow-ups:

- "Why does I2C need pull-up resistors?" (open-drain; the resistor sets the rise time; too weak is slow, too strong wastes current and can't be pulled low)
- "What does a NACK on the address tell you?" (nobody at that address: wiring, power, or the wrong address)
- "Your sensor reads 0xFF. What do you check?" (did the read return any bytes; is SDA connected; power; the address)
- "What's a repeated START and why use it?"
