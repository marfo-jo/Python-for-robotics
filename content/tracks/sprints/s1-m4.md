## Goal, and why it matters

Send each sample as a fixed **23-byte binary frame** with a sync pattern, a sequence number, and a checksum, and write a Python parser that **resynchronizes** after garbage, **rejects** corrupted frames, and **counts** what it lost.

This is the heart of the project for interviews. "Design a serial protocol" and "what happens when bytes get lost?" are standard embedded questions, and most candidates answer in generalities. You'll answer with a frame you designed, a parser you wrote, tests that inject faults, and counters you watched on real hardware. It's also the same problem every fieldbus solves (Modbus RTU frames with a CRC, CAN frames with a CRC and an ACK slot), so connect it to what you already know from PLC work.

## Why binary?

| | CSV text (1.3) | Binary frame (1.4) |
|---|---|---|
| Size per sample | 30 to 61 bytes, variable | 23 bytes, fixed |
| Finding the start of a sample | newline | sync bytes `A5 5A` |
| Detecting corruption | barely (only if a field stops being a number) | an 8-bit Fletcher checksum over every payload byte |
| Detecting lost samples | only by `t_ms` gaps | sequence number |
| Human-readable | yes, in Serial Monitor | no: Serial Monitor shows junk |
| CPU on the Uno | number-to-text conversion for 8 fields | none: copy bytes |

Text is great for bring-up. Binary is what you ship: smaller, fixed-length, and checkable. Saying this trade-off clearly is half of a good interview answer.

## The frame format (this is the spec)

![The 23-byte frame: sync A5 5A, seq, t_ms as 4 little-endian bytes, seven int16 values little-endian, then CK_A and CK_B](content/tracks/sprints/img/imu-frame.svg)

| Offset | Size | Field | Type | Notes |
|---|---|---|---|---|
| 0 | 1 | sync 1 | `0xA5` | |
| 1 | 1 | sync 2 | `0x5A` | |
| 2 | 1 | `seq` | `uint8` | +1 every 10 ms tick, wraps 255 → 0 |
| 3 | 4 | `t_ms` | `uint32`, little-endian | `millis()` at the read |
| 7 | 14 | `ax, ay, az, temp, gx, gy, gz` | 7 × `int16`, little-endian | raw counts, register order |
| 21 | 1 | `CK_A` | `uint8` | checksum, see below |
| 22 | 1 | `CK_B` | `uint8` | |

Total: **23 bytes**. Little-endian means **low byte first**: `t_ms = 0x01020304` is sent as `04 03 02 01`, and `ax = -1` (`0xFFFF`) is sent as `FF FF`, and `ax = 256` (`0x0100`) as `00 01`.

Notice the twist: the MPU-6050 gives you each value **big-endian** (high register first), and this frame wants **little-endian**. Your firmware has to put the bytes in the frame's order. Don't rely on copying a C `struct` into the buffer: on the AVR it happens to have no padding and to be little-endian, but on another processor (the ESP32 you'll use later, or a desktop) padding and byte order can differ. Filling a `uint8_t buf[23]` explicitly, byte by byte with shifts, is portable and obvious to a reviewer.

### The checksum: 8-bit Fletcher

Computed over **bytes 2 through 20** (sequence number, timestamp, and payload; never the sync bytes):

```
CK_A = 0, CK_B = 0
for each byte b in bytes 2..20:
    CK_A = (CK_A + b) mod 256
    CK_B = (CK_B + CK_A) mod 256
```

This is the same checksum the u-blox UBX GPS protocol uses. Why two sums? `CK_A` alone is a plain sum, and a plain sum (or XOR) can't tell `01 02` from `02 01`. `CK_B` adds up the running sums, so each byte's **position** affects it, which catches swapped bytes. It's still weak against some multi-bit errors; a CRC-16 is stronger (a good stretch goal, and a good interview remark).

In C on the Uno, `uint8_t` arithmetic wraps modulo 256 by itself. In Python, `& 0xFF` or `% 256` after each addition does the same.

### Sequence numbers and drops

`seq` advances on **every 10 ms tick**, even if that tick's I2C read failed and you didn't send a frame. The host then sees a gap in `seq` for any sample that didn't arrive, whatever the reason (failed read, lost bytes, a corrupted frame). One counter covers every way to lose a sample.

Because `seq` is 8 bits, the gap between two received frames is computed **modulo 256**: from 254 to 1 is a gap of 2 missed frames (255 and 0), and from 255 to 0 is no gap at all. With 100 frames/s, a single burst of more than 255 lost frames (2.56 s) would alias; say that limitation in your README.

### Bandwidth check

23 bytes × 10 bits per byte (8N1) × 100 frames/s = 23,000 bit/s, which is **20% of 115200 baud**. The 64-byte transmit buffer holds two whole frames, and each frame drains in 2 ms. Plenty of margin.

## `imu_packet.py`, the Python spec

Write `host/imu_packet.py`. Names and signatures must match, because the tests import them. Use only the standard library (`struct` is the natural tool).

```python
SYNC = b"\xA5\x5A"
FRAME_LEN = 23
```

### `checksum(data) -> tuple[int, int]`

Return `(ck_a, ck_b)` for `data` (bytes), as defined above. `checksum(b"")` is `(0, 0)`; `checksum(b"\x01\x02\x03")` is `(6, 10)`. Work that one out by hand before you code it.

### `build_frame(seq, t_ms, values) -> bytes`

Build one complete 23-byte frame. `values` is a sequence of exactly 7 ints `(ax, ay, az, temp, gx, gy, gz)`. Raise `ValueError` if `seq` isn't 0..255, `t_ms` isn't 0..2^32 - 1, there aren't exactly 7 values, or any value is outside the `int16` range. You'll use this function to **generate test data**, and as the Python reference for your C framing code.

### `parse_frame(frame) -> tuple or None`

Given exactly one candidate frame (bytes), return `(seq, t_ms, values)`, where `values` is a tuple of 7 ints, or `None` if the length isn't 23, the sync bytes are wrong, or the checksum doesn't match.

### `class PacketParser`

A stream parser that accepts bytes in **any** chunk sizes (one byte at a time, or 1000 at once, or a frame split across two reads) and returns complete samples.

- `PacketParser()`: no arguments. Four public integer counters, all starting at 0:
  - `good`: frames accepted
  - `corrupt`: candidate frames that started with `A5 5A` but failed the checksum
  - `dropped`: frames that never arrived, inferred from `seq` gaps (modulo 256) between accepted frames
  - `skipped_bytes`: bytes thrown away while hunting for a sync
- `feed(data) -> list`: append `data` to an internal buffer, extract every complete valid frame, and return their `(seq, t_ms, values)` tuples **in order**. Keep any incomplete tail for the next call. Raise `TypeError` if `data` isn't `bytes` or `bytearray`.

**The resync rules** (follow them exactly; the counters are tested):

1. Look for `A5 5A` in the buffer. Every byte before it is discarded and added to `skipped_bytes`. If there's no sync at all, discard everything **except** a final `0xA5`, which might be the first half of a sync that's still arriving.
2. If fewer than 23 bytes are available from the sync, stop and wait for more data.
3. If the 23 bytes starting at the sync parse as a valid frame: accept it, remove those 23 bytes, add the `seq` gap to `dropped` (except for the very first frame), and add 1 to `good`.
4. If they don't: add 1 to `corrupt`, discard **only the first byte** (add 1 to `skipped_bytes`), and go back to rule 1.

**Rule 4 is the one everybody gets wrong.** The tempting version throws away all 23 bytes of a bad frame. But suppose a frame got cut short (a byte was lost on the wire). The 23-byte "candidate" then contains the start of the *next, perfectly good* frame. Throwing away 23 bytes throws that good frame away too, and with steady byte loss you can lose almost everything. Discarding one byte and searching again finds it. There's a test for exactly this case.

Also notice that `A5 5A` can appear **inside** a payload (an `int16` of 23205 is sent as `A5 5A`). The checksum is what saves you from false syncs; there's a test for that too.

## The firmware side

Start from your 1.2 sketch (keep 1.2 intact: copy it into `firmware/imu_binary/`). Changes:

1. Remove all text output. Startup `#` lines would reach the binary parser as junk bytes; rule 1 would skip them (and count them in `skipped_bytes`), but it's cleaner to drop them, or send them only before the stream starts.
2. A `uint8_t seq` that increments every tick.
3. A function that fills a 23-byte buffer from `seq`, `t_ms`, and the seven values, then computes and appends the checksum. Suggested signature:

```c
// Fills frame[0..22] per the Sprint 1 frame spec.
void buildFrame(uint8_t frame[23], uint8_t seq, uint32_t t_ms, const int16_t values[7]);
```

4. Send it with `Serial.write(frame, 23)`. **Not** `Serial.print`: `print` converts numbers to text.
5. A fault-injection switch for testing the host, for example `#define FAULT_EVERY 0` (off), and when it's nonzero, flip one bit in a payload byte of every Nth frame **after** computing the checksum.

You can't check the output in Serial Monitor any more. Verify it with Python: a tiny script that reads 46 bytes and prints them as hex (`data.hex(" ")`), and then your real parser.

## Common beginner mistakes

- Big-endian in the frame because "that's what the MPU sends". The spec says little-endian; follow the spec, then convert.
- Including the sync bytes in the checksum, or leaving out the sequence number.
- Throwing away 23 bytes on a checksum failure (rule 4).
- Dropping a lone trailing `0xA5`: feeding one byte at a time then loses **every** frame.
- Counting a wrap from 255 to 0 as -256 drops.
- Resetting `seq` to 0 in the firmware when a read fails.
- `ser.readline()` on a binary stream. There are no lines; `0x0A` is just a byte that appears in data.

## Hints

<details><summary>Hint 1 (nudge)</summary>

Build and test in this order: `checksum` (hand-check 3 bytes), then `build_frame` (compare against the exact bytes in the test), then `parse_frame` (round trip), and only then `PacketParser`. The parser is a loop over a `bytearray` buffer: `find` the sync, decide, delete bytes from the front, repeat.

</details>

<details><summary>Hint 2 (approach)</summary>

`build_frame`: validate, then `struct.pack` with a format that means "little-endian, one unsigned byte, one unsigned 32-bit int, seven signed 16-bit ints" (look up the format characters `<`, `B`, `I`, `h`). Prepend the sync and append the two checksum bytes computed over the packed body.

`PacketParser.feed`: keep a `bytearray` in `self`. In a `while True` loop: find the sync; handle "not found" (rule 1) and break; discard bytes before it; if fewer than 23 bytes remain, break; try `parse_frame` on the first 23 bytes; on success, delete 23 bytes, update counters, append the sample; on failure, delete 1 byte and update counters. Keep the last accepted `seq` in `self` (start it as `None`).

</details>

<details><summary>Hint 3 (pseudocode): the parser loop</summary>

```
feed(data):
    if data is not bytes or bytearray: raise TypeError
    append data to buffer
    out = empty list
    loop forever:
        i = position of SYNC in buffer
        if not found:
            keep = 1 if the buffer's last byte is 0xA5 else 0
            skipped += len(buffer) - keep
            remove all but the last `keep` bytes
            break
        skipped += i; remove the first i bytes
        if len(buffer) < FRAME_LEN: break
        sample = parse_frame(first FRAME_LEN bytes)
        if sample is None:
            corrupt += 1; skipped += 1; remove 1 byte
            continue
        remove FRAME_LEN bytes
        if last_seq is not None: dropped += (seq - last_seq - 1) mod 256
        last_seq = seq; good += 1; add sample to out
    return out
```

</details>

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| `good` stays 0, `skipped_bytes` climbs | Firmware still prints text, or the sync bytes are reversed (`5A A5`) | Hex-dump 46 bytes and look for `a5 5a` every 23 bytes. |
| Every frame is `corrupt` | Checksum range off by one (sync included, or one byte short), or wrong byte order | Compare one frame from the Uno with `build_frame` for the same values. |
| Values look like `16384` → `64` | Byte order mixed up between firmware and parser | The frame is little-endian: low byte first. |
| `dropped` grows steadily, `corrupt` = 0 | The host is too slow and the OS serial buffer overflowed, or the firmware skips ticks | Don't print every sample; read bigger chunks. Check the firmware's overrun counter. |
| `corrupt` and `dropped` jump together when you touch the cable | Real noise or a bad USB cable | Good: your counters work. Try another cable. |
| Python reads nothing at all | Serial Monitor still open, or a wrong COM port | Close the monitor; check `python -m serial.tools.list_ports -v`. |
| The first frame after opening the port is missing | Expected: the Uno resets (DTR), and you opened mid-frame | Rule 1 handles it. |
