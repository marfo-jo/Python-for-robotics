## Goal, and why it matters

Run a whole test campaign (many step inputs, both directions, repeated) with **one command**, safely, and get back clean, self-describing logs plus a summary plot of steady-state speed against PWM.

This is test automation, the core of test and validation roles: a scripted sequence, a safe state, abort limits, and data you can trust without having watched the test. It's also where your maintenance experience reads as engineering: a test plan with pass/fail limits is a work instruction with a data logger attached.

## Safety

The script is now in charge of a motor while you're not touching anything, so the safety logic is part of the deliverable:

- **Software limits** (your choice of numbers; these are sensible starting points): current above **1.5 A** for more than 0.3 s; motor-can temperature above **60 °C**; bus voltage below **10.5 V** (supply sagging or fuse blown); no data for **0.5 s**. Any one aborts the run.
- **Firmware watchdog** from 2.1 as the backup if Python dies.
- **`finally:`** around the whole run: send `STOP` and close the port and files, no matter what.
- **The supply switch** within reach, and you present for every run.

## Step 1: physical units

From the stream fields in 2.1 (do the conversions in `rig.py`, once):

| Quantity | From | Conversion |
|---|---|---|
| time (s) | `t_ms` | t_ms / 1000 |
| shaft angle (rad) | `count` | count × 2π / CPR |
| speed (rad/s) | change in `count` over change in `t_ms` | (Δcount / CPR) × 2π / Δt |
| current (A) | `shunt_raw` | shunt_raw × 10 µV / 0.1 Ω = shunt_raw × 0.0001 |
| bus voltage (V) | `bus_raw` | (bus_raw shifted right by 3 bits) × 0.004 |
| duty | `pwm` | pwm / 255 |

**Speed resolution: do the math.** Over one 10 ms tick, a change of one count is (1 / CPR) × 2π / 0.01 s. With CPR ≈ 1500 that's about **0.42 rad/s** (4 rpm) per count: the speed signal is quantized in steps of 0.42 rad/s. Differencing over a longer window (5 ticks = 50 ms) gives 5× finer resolution but adds 25 ms of lag. That's the classic resolution-versus-delay trade-off of encoder speed estimation; state your choice and why in the README. (For system ID in 2.3 you can difference over several samples offline; for the live PI loop in 2.4 you'll feel the trade-off for real.)

## Step 2: a test plan as data, not code

Keep the plan in a JSON file so changing a test never means editing the runner. A plan might look like:

```json
{
  "name": "open_loop_steps_v1",
  "settle_s": 1.0,
  "step_s": 3.0,
  "rest_s": 2.0,
  "pwm_levels": [60, 90, 120, 150, 180, 210, 255, -60, -90, -120, -150, -180, -210, -255],
  "repeats": 3,
  "shuffle_seed": 1234,
  "limits": {"max_current_a": 1.5, "max_temp_c": 60.0, "min_bus_v": 10.5, "max_silence_s": 0.5}
}
```

Each step: hold `PWM 0` for `settle_s` (record the true starting state), step to the level for `step_s`, then back to 0 for `rest_s` (the motor coasts down: that's a second, free step response to look at later).

**Why shuffle?** If you always run the levels in increasing order, the motor is warmest during the highest-PWM tests, and you can't tell a temperature effect from a PWM effect. Randomizing the order (with a **fixed seed**, so it's reproducible) spreads the warm-up across all levels. This is basic experimental design, and it's a great interview detail.

**Why repeat?** Three repeats tell you the test's repeatability. If repeats of the same step differ by more than a few percent, find out why before fitting any model.

## Step 3: the runner

What `step_test.py` does, in order:

1. Load the plan; build the shuffled list of steps.
2. Open the port (with a timeout), wait for the header line, then start logging.
3. For each step, for each phase (settle, step, rest): send the PWM command, then keep reading samples until the phase's time is up. **Every 100 ms, resend the current command** (or `PING`) so the watchdog stays quiet.
4. On every sample: check the limits. If one trips, stop the plan, send `STOP`, and record which limit and when.
5. Log every sample with extra columns: `step_id`, `phase`, and `cmd_pwm` (what you asked for, which differs from the `pwm` the firmware reports if the watchdog ever fires).
6. `finally:` send `STOP`, close everything, and write the metadata JSON.

**Use the device's clock.** Phase timing can use the host's clock, but every analysis uses the Uno's `t_ms`. The host clock jitters by milliseconds; the Uno's timestamps are what the samples were really taken at.

## Step 4: summary plots

- **One step response:** speed, current, and bus voltage against time on three stacked axes (see bg-plot). You'll see the current spike at the step (the motor's back-EMF is 0 at standstill, so only the winding resistance limits the current) and decay as the speed rises. Point it out in your README: it's the electrical equation of motion, visible in your data.
- **Steady-state speed vs PWM:** average the speed over the last second of each step; plot all repeats as points, both directions. You'll see the **deadband** around 0 and a roughly linear region above it. Mark the deadband on the plot.

## Common beginner mistakes

- Sending one `PWM` command per phase and nothing else: the watchdog stops the motor after 0.5 s, and the "step response" is a 0.5 s pulse.
- Calling `STOP` only at the end of the happy path. Ctrl+C leaves the motor running until the watchdog fires; an exception before the watchdog existed would leave it running forever.
- Computing speed from consecutive samples and plotting it raw, then trying to fit a model to a staircase. Know your quantization; difference over a few samples for analysis.
- Using host time (`time.time()`) for the analysis.
- Hard-coding the plan in the script.
- Overwriting logs. Timestamped names, as in Sprint 1.

Drive the motor by hand from the session (`PWM 120`, read a few samples, `STOP`) before writing any automation. Then the runner is just a loop over phases that uses those functions.

</details>

<details><summary>Hint 2 (approach)</summary>

Structure the runner as: `load_plan(path)` returns the plan dict and the shuffled step list; `run_phase(link, pwm, seconds, writer, limits)` sends the command, loops reading samples, resends the command every 100 ms, writes each row, and returns either `None` or an abort reason; `main()` opens everything in `with` blocks, loops over steps and phases, stops at the first abort reason, and does the stop-and-metadata work in `finally:`.

</details>

<details><summary>Hint 3 (pseudocode)</summary>

```
main:
    plan, steps = load_plan(path)
    reason = "completed"
    open the port and the log file (with-blocks)
    try:
        wait for the header line
        for each (step_id, level) in steps:
            for (phase, pwm, seconds) in [("settle", 0, settle_s), ("step", level, step_s), ("rest", 0, rest_s)]:
                reason_now = run_phase(link, pwm, seconds, writer, limits, step_id, phase)
                if reason_now: reason = reason_now; stop all loops
    except KeyboardInterrupt: reason = "operator stop"
    finally:
        send STOP (twice is fine); flush and close; write metadata with reason

run_phase:
    send PWM pwm; last_send = now; end = now + seconds
    while now < end:
        sample = read one parsed sample (or None on timeout)
        if no sample for max_silence_s: return "no data"
        if now - last_send >= 0.1: resend; last_send = now
        if a limit is exceeded (current held over max for 0.3 s, temp, bus V): return that limit's name
        write the row with step_id, phase, pwm
    return None
```

</details>

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| Every step is cut off after 0.5 s | No heartbeat | Resend the command every 100 ms. |
| `# WATCHDOG` lines during a run | Heartbeat too slow, or the script blocked (a plot window, a long `print`) | Never block inside the run loop; plot afterwards. |
| The run aborts on "no data" at the start | The Uno is resetting after the port opens | Wait for the header before starting the plan. |
| Overcurrent abort on every high-PWM step | The inrush spike at each step exceeds your threshold | That's why the limit has a time condition (held for 0.3 s), not a single sample. |
| Uno resets at the start of high-PWM steps | Supply dip or noise (see 2.1 troubleshooting) | Star ground, decoupling, twisted motor leads; check the bus voltage log for dips. |
| Repeats of the same step differ by more than about 5% | Temperature drift, a loose coupler, or the supply setting changed | Look at the temperature column; check the mechanics; log the bus voltage. |
| Steady-state speed looks like a staircase | Encoder quantization over 10 ms | Difference over several samples for the summary. |
| Speed spikes to huge values for one sample | A dropped line made Δt twice as long but you divided by 10 ms | Always divide by the actual Δt from `t_ms`. |
