**About 30 minutes.** By the end you'll have two working C toolchains, you'll know what each one does to your source code, and you'll be able to explain why an Arduino sketch has no `main()`. That last one is a real interview question.

## Why C, and why two toolchains?

Embedded, test, and controls co-op postings almost all list C. The firmware on the Uno in Sprint 1 is C (strictly, C++ compiled by avr-gcc, but the parts you'll write are plain C style). Python runs on the host; C runs on the metal.

You'll use two separate toolchains, and each is a different target:

| | Desktop C (the VM) | Firmware C (the Uno) |
|---|---|---|
| Where you type | Ubuntu 22.04 VM terminal | Arduino IDE on Windows |
| Compiler | `gcc` (targets x86-64) | `avr-gcc` (targets the ATmega328P) |
| Who calls your code | the operating system calls `main()` | the Arduino core's `main()` calls `setup()` and `loop()` |
| Output goes to | the terminal (`printf`) | the USB serial link (`Serial.print`) |
| Best for | learning the language, fast edit-run cycles, unit tests | touching real pins, timers, I2C |

Why learn C on the desktop at all when the goal is the Uno? Because the edit-compile-run loop on the desktop takes about one second and you see every message. On the Uno you upload, open a monitor, and debug through a 115200-baud keyhole. Most of the language (types, pointers, structs, bit operations) behaves the same on both, so you learn it where feedback is fast, then carry it to the board. You'll also see the places where the two targets **differ** (C2 is entirely about one of them).

## Part 1: gcc in the Ubuntu VM

### Install and check

Open a terminal in the VM and run:

```bash
sudo apt update && sudo apt install build-essential
gcc --version
```

`build-essential` is a meta-package: it pulls in `gcc`, `g++`, `make`, and the C standard library headers. `sudo apt update` refreshes the package list first (skip it and apt may try to download versions that no longer exist). The `&&` means "run the second command only if the first one succeeded", the same idea as an interlock in a ladder rung.

`gcc --version` should print something like `gcc (Ubuntu 11.4.0-1ubuntu1~22.04) 11.4.0`. Ubuntu 22.04 ships gcc 11. If you get `command not found`, the install did not finish: re-run it and read the last few lines of output.

### Your first program, line by line

```c
#include <stdio.h>

int main(void)
{
    printf("Hello from the VM!\n");
    return 0;
}
```

- `#include <stdio.h>` pastes in the declarations for standard input/output, including `printf`. It's a **preprocessor** directive (more on that below). Without it the compiler doesn't know what `printf` is.
- `int main(void)` is where the operating system starts your program. `int` is the type of value it returns; `void` means it takes no arguments.
- `printf("...\n")` prints text. Unlike Python's `print`, it does **not** add a newline for you: `\n` is your job.
- Every statement ends with `;`. Blocks are wrapped in `{ }`. Indentation is for humans only; C ignores it (unlike Python).
- `return 0;` hands an exit code to the shell. `0` means success, anything else means failure. In the terminal, `echo $?` right after a program shows its exit code. Scripts (and CI pipelines, and `check.sh`) rely on this, much like a PLC reading a "done OK" bit from a drive.

### Compile and run

```bash
gcc -Wall -Wextra -std=c11 hello.c -o hello && ./hello
```

| Piece | What it does | Why you want it |
|---|---|---|
| `gcc` | the compiler driver: runs the preprocessor, compiler, assembler, and linker for you | one command for the whole pipeline |
| `-Wall` | turns on the most useful warnings (unused variables, wrong `printf` formats, missing `return`) | most real C bugs show up as warnings first |
| `-Wextra` | turns on more warnings (unused parameters, signed/unsigned comparisons) | catches the subtle ones |
| `-std=c11` | compile as ISO C11, the 2011 standard | same language rules every time, on every machine |
| `hello.c` | the source file | |
| `-o hello` | name the output executable `hello` | without it gcc names it `a.out` |
| `./hello` | run the program in the current directory (`.`) | Linux doesn't search the current folder unless you say `./` |

`check.sh` (used below) adds one more flag: **`-Werror`**, which turns every warning into an error. That's deliberate. A warning in C is the compiler saying "this is legal but probably not what you meant", and in firmware "probably wrong" becomes a field failure. Treat warnings the way you'd treat a fault light on a drive: you don't run the line until you know why it's lit.

Try this right now to see a warning:

```c
#include <stdio.h>

int main(void)
{
    int speed = 42;
    printf("speed = %d\n");
    return 0;
}
```

gcc with `-Wall` says something like `warning: format '%d' expects a matching 'int' argument`. Without `-Wall`, it compiles silently and prints garbage, whatever happened to be in that register. That's the whole case for warnings in one example.

### What gcc actually does: the pipeline

"Compile" is really four stages. Knowing them tells you **which stage** an error came from, which tells you where to look.

```
 hello.c ──► [1 preprocess] ──► [2 compile] ──► [3 assemble] ──► hello.o ──► [4 link] ──► hello
            #include, #define    C to assembly    assembly to      object      + C library
            pasted in as text                     machine code     file        (printf lives here)
```

1. **Preprocess**: text substitution only. `#include` pastes files in; `#define LED_PIN 13` replaces names. You can see the result with `gcc -E hello.c | tail`.
2. **Compile**: C becomes assembly for the target CPU. Syntax errors and type errors come from here (`error: expected ';' before 'return'`).
3. **Assemble**: assembly becomes machine code in an **object file** (`hello.o`). You can stop here with `gcc -c hello.c`.
4. **Link**: the linker joins your object file with the libraries that hold the code you called. `printf` isn't in your file; it's in the C library, and the linker wires the call to it. Errors here look different: `undefined reference to 'pritnf'` means the compiler accepted a call, but the linker couldn't find anything by that name.

The EE analogy: preprocessing and compiling are like turning a schematic into a netlist; linking is like the PCB tool connecting your board's nets to the connector pinout of an off-the-shelf module you didn't design.

## Part 2: the Arduino IDE on Windows

The IDE is already installed. Plug in the Uno with a USB cable.

1. **Board**: Tools → Board → Arduino AVR Boards → **Arduino Uno**. This picks the compiler target (ATmega328P at 16 MHz) and the pin map.
2. **Port**: Tools → Port → the COM port that appears when you plug the board in (for example `COM3`, often labeled "Arduino Uno"). Not sure which one? Unplug the board, look at the list, plug it back in, and see which port appeared. If none appears, try another cable: plenty of USB cables are charge-only, with no data lines.
3. **Blink**: File → Examples → 01.Basics → Blink. Click **Upload** (the right arrow). The output pane shows the compile, then the upload; the on-board LED (pin 13, `LED_BUILTIN`) blinks once per second.
4. **Serial**: add `Serial.begin(115200);` inside `setup()`, and `Serial.println("tick");` inside `loop()`. Upload, then open Tools → **Serial Monitor** and set the baud dropdown (bottom right) to **115200**.

`Serial.begin(115200)` configures the UART at 115200 bits per second. The Serial Monitor must use the **same** rate. If the two disagree, you see garbage characters, exactly like a scope's UART decoder set to the wrong baud rate. You'll use 115200 for every sketch in this course and in Sprint 1.

### The firmware pipeline: compile → link → upload

When you click Upload, the IDE runs the same four stages as gcc, using **avr-gcc**, then two more steps:

```
 sketch.ino ─► [Arduino prep] ─► [avr-gcc: preprocess, compile, assemble] ─► [link with the Arduino core] ─► sketch.hex ─► [avrdude upload] ─► flash
               adds #include                                                  core = main(), Serial, pinMode     machine code      over USB serial
               <Arduino.h>                                                    millis(), digitalWrite ...         as hex text       to the bootloader
```

- The IDE adds `#include <Arduino.h>` to the top of your sketch and generates function prototypes for you. (That's why a `.ino` lets you call a function defined lower in the file, while a plain `.c` file does not.)
- The **Arduino core** is a library of C/C++ that includes `main()`, `Serial`, `pinMode`, `millis()`, and friends. The linker joins your sketch to it.
- **avrdude** sends the `.hex` file over USB serial to the **bootloader**, a small program already sitting in the Uno's flash that writes the new program into the rest of flash, then jumps to it.

The output pane ends with something like `Sketch uses 924 bytes (2%) of program storage space`. That's the linker reporting how much flash you've used (32 KB minus 0.5 KB for the bootloader = 32256 bytes) and how much RAM your globals take (2048 bytes total). On a desktop you never think about this. On the Uno, 2 KB of RAM is a real constraint.

### Where is main()? (the scan-cycle model)

A desktop C program **must** have `main()`. An Arduino sketch has `setup()` and `loop()` and no `main()` at all. Where did it go?

It's in the Arduino core. This is the real code from `cores/arduino/main.cpp` in the AVR core you have installed (lightly trimmed):

```c
int main(void)
{
    init();          // set up timers (millis), the ADC, PWM

    setup();         // YOUR code, once

    for (;;) {       // forever
        loop();      // YOUR code, again and again
        if (serialEventRun) serialEventRun();
    }

    return 0;        // never reached
}
```

`for (;;)` is a loop with no stop condition: it runs until power is removed. If you've worked with PLCs, you already know this model:

| PLC | Arduino |
|---|---|
| power-up / first-scan initialization | `init()` + `setup()` |
| the scan: read inputs, solve logic, write outputs | one pass through `loop()` |
| scan repeats forever | `for (;;) { loop(); }` |
| a slow rung stretches the scan time and makes everything late | a `delay(500)` inside `loop()` stalls **everything else** for 500 ms |

That last row is why, in C14, you'll replace `delay()` with non-blocking `millis()` timing: the same reason you'd never put a long blocking wait in a PLC rung.

And on the desktop, `return 0` from `main()` ends the program and hands control back to the OS. On the Uno there's no OS to return to, which is why the core never lets `main()` return.

## Common beginner mistakes

- **Forgetting `\n`** in `printf`. Your output runs together on one line, and `check.sh` reports a diff.
- **Reading the last error instead of the first.** One missing `;` can produce ten errors. Fix the first one, recompile, repeat.
- **Running `hello` instead of `./hello`**, then getting `command not found`.
- **Editing the file and forgetting to recompile.** `./hello` runs the old executable until you run `gcc` again.
- **Wrong baud rate in the Serial Monitor**: garbage characters. Match it to `Serial.begin()`.
- **Serial Monitor open in another program** (or a Python script holding the port): upload fails with "port busy" or "access denied". Close the other user of the COM port.
- **Ignoring warnings because "it ran anyway".** It ran *this time*.

   ```bash
   gcc -Wall -Wextra -std=c11 hello.c -o hello && ./hello
   ```

   ```bash
   bash ../../../local/c-embedded/check.sh hello.c
   ```
