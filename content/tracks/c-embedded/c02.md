**About 30 minutes.** In Python, an integer can grow as large as you like. In C, every variable is a fixed number of bits, like a hardware register. Pick the wrong width and the value silently wraps around, and on an Uno the "wrong width" is often plain `int`. This page is about choosing widths on purpose.

## Types are register widths

Each C integer type is a box with a fixed number of bits. The value can't spill out of the box. Think of an 8-bit counter IC (a 74HC590, say): after 255 the next clock gives 0. C's unsigned types behave the same way.

The basic types are `char`, `short`, `int`, `long`, and `long long`. Here's the trap: **the C standard only sets minimum sizes**, and each platform picks its own.

| Type | C standard minimum | x86-64 Linux (your VM) | Uno (ATmega328P, avr-gcc) |
|---|---|---|---|
| `char` | 8 bits | 1 byte | 1 byte |
| `short` | 16 bits | 2 bytes | 2 bytes |
| `int` | 16 bits | **4 bytes** | **2 bytes** |
| `long` | 32 bits | **8 bytes** | **4 bytes** |
| `long long` | 64 bits | 8 bytes | 8 bytes |
| `float` | (IEEE single, in practice) | 4 bytes | 4 bytes |
| `double` | (IEEE double, in practice) | **8 bytes** | **4 bytes** (avr-gcc makes `double` the same as `float`) |

Read the bold rows again. The same line of C, `int count = 40000;`, works on your VM and is broken on your Uno. (Bonus fact for interviews: on 64-bit **Windows**, `long` is 4 bytes, not 8. Three platforms, three answers. That's exactly why the next section exists.)

### sizeof: ask the compiler

`sizeof(type)` or `sizeof variable` gives the size in **bytes**, worked out at compile time. Its result has type `size_t`, and the `printf` format for `size_t` is `%zu`:

```c
printf("sizeof(int) = %zu\n", sizeof(int));     // VM: 4   Uno: 2
long ticks = 0;
printf("sizeof ticks = %zu\n", sizeof ticks);   // VM: 8   Uno: 4
```

`sizeof` is how you stop guessing. You'll use it constantly once you build packets in C9 (a 14-byte IMU burst read must be exactly 14 bytes).

## stdint.h: say exactly how many bits you mean

Because `int` and `long` change size between platforms, embedded code uses the **fixed-width types** from `<stdint.h>`. The name tells you everything:

| Type | Bits | Signed? | Range | Typical use |
|---|---|---|---|---|
| `uint8_t` | 8 | no | 0 to 255 | a byte from I2C, a register value, a PWM duty on the Uno |
| `int8_t` | 8 | yes | −128 to 127 | a small signed offset |
| `uint16_t` | 16 | no | 0 to 65535 | a 10-bit ADC reading (fits with room to spare) |
| `int16_t` | 16 | yes | −32768 to 32767 | **MPU-6050 accelerometer and gyro readings** (Sprint 1) |
| `uint32_t` | 32 | no | 0 to 4294967295 | `millis()` and `micros()` timestamps |
| `int32_t` | 32 | yes | about ±2.1 billion | encoder counts (Sprint 2) |

`u` means unsigned, the number is the bit count, `_t` means "this is a type". `uint8_t` is 8 bits on the Uno, on the VM, on a Pi, and on an STM32. When a datasheet says "16-bit two's complement register", you write `int16_t`, and your code means the same thing everywhere.

Why embedded code insists on these:

1. **Registers and packets have fixed widths.** The MPU-6050's `ACCEL_XOUT` is 16 bits signed. Store it in an `int16_t` and the sign comes out right on every platform.
2. **RAM is tiny.** The Uno has 2048 bytes. An array of 500 `uint8_t` samples takes 500 bytes; as `long` it takes 2000 and you've used the whole chip.
3. **Portability.** Code you test on the VM (fast feedback) behaves the same on the board.

A useful rule: use `int` only for small values that are local to a function (loop counters up to a few hundred). For anything that touches hardware, data, or time, use a `stdint.h` type.

## Signed vs unsigned

An **unsigned** n-bit type uses all n bits for magnitude:

$$0 \le x \le 2^{n} - 1$$

A **signed** type uses **two's complement**, where the top bit has a negative weight:

$$-2^{n-1} \le x \le 2^{n-1} - 1$$

So 8 bits give 0 to 255 unsigned, or −128 to 127 signed. The bit pattern `1111 1111` (0xFF) is 255 as a `uint8_t` and −1 as an `int8_t`. **Same bits, different meaning.** The type is how the code is told to read the bits, just as a datasheet register map tells you whether a field is signed. In Sprint 1, reading the IMU's two bytes as unsigned instead of signed turns a small negative tilt into a huge positive number. That's one of the classic Sprint 1 bugs.

## Overflow and wraparound

What happens when a result doesn't fit?

**Unsigned types wrap around, and C guarantees it.** The result is taken modulo 2ⁿ, like an odometer:

```c
uint8_t a = 255;
a = a + 1;          // 0
uint8_t b = 0;
b = b - 1;          // 255
uint16_t c = 65535;
c = c + 1;          // 0
```

**Signed overflow is undefined behavior (UB).** If a signed calculation goes past its maximum, the C standard says nothing about the result. The program might wrap to a negative number, or the optimizer might assume overflow "can't happen" and delete your range check entirely. UB means "anything at all, and maybe something different next time you change compiler flags". You must design so that signed overflow never happens. (In PLC terms: it isn't a fault that trips a known alarm. It's a fault with no defined behavior, which is worse.)

A subtle but important detail: C does arithmetic in at least `int` width. On the VM, `int16_t t = 32767; t = t + 1;` computes `32768` as a 32-bit `int` (no overflow), then **converts** it back into 16 bits. That conversion is *implementation-defined*, and gcc defines it as wrapping, so you get −32768. On the Uno, `int` itself is 16 bits, so `int t = 32767; t++;` is a true signed overflow: undefined behavior.

### The classic Uno bug: int and millis()

`millis()` returns milliseconds since power-up as an `unsigned long` (32 bits on the Uno). Beginners write:

```c
int lastPrint = 0;

void loop() {
  int now = millis();              // BUG: 32-bit value squeezed into a 16-bit int
  if (now - lastPrint >= 1000) {
    Serial.println("tick");
    lastPrint = now;
  }
}
```

It works on the bench for a while. A 16-bit signed `int` tops out at 32767, which is 32.767 seconds of milliseconds. After that, `now` turns negative (40000 ms becomes −25536 when it's squeezed into 16 bits) and the timing logic misbehaves: ticks stop, or come in a burst. It passes a quick bench test and fails in the field after half a minute, which is the worst kind of bug. With a 32-bit `int` (as on the VM) the same mistake would take about 24.8 days to show up, which is how this bug survives code review: it "works on my machine".

The fix: store time in the type `millis()` returns.

```c
uint32_t lastPrint = 0;

void loop() {
  uint32_t now = millis();
  if (now - lastPrint >= 1000) {   // unsigned subtraction: correct even across the wrap
    Serial.println("tick");
    lastPrint = now;
  }
}
```

Even `uint32_t` wraps, after 4294967295 ms, which is about 49.7 days. But **unsigned subtraction gives the right elapsed time across the wrap**: if `lastPrint` is 4294967290 (6 ms before the wrap) and `now` is 14 (14 ms after), then `now - lastPrint` is 20, modulo 2³². That's why the pattern is `now - last >= interval`, and never `now >= last + interval` (that sum wraps and the comparison breaks). You'll prove the 20 in the exercise.

## printf format specifiers

On the desktop, `printf` needs to know the type of each argument. A mismatch is UB, and `-Wall` warns about most of them.

| Specifier | Type | Example | Prints |
|---|---|---|---|
| `%d` | `int` (signed) | `printf("%d", -5)` | `-5` |
| `%u` | `unsigned int` | `printf("%u", 40000u)` | `40000` |
| `%ld` | `long` | `printf("%ld", 100000L)` | `100000` |
| `%lu` | `unsigned long` | `printf("%lu", 4000000000UL)` | `4000000000` |
| `%x` / `%X` | `unsigned int`, in hex | `printf("0x%X", 255u)` | `0xFF` |
| `%zu` | `size_t` (from `sizeof`) | `printf("%zu", sizeof(int))` | `4` |
| `%f`, `%.1f` | `double` | `printf("%.1f", 49.71)` | `49.7` |

What about `uint32_t`? It's `unsigned int` on the VM but `unsigned long` on the Uno, so neither `%u` nor `%lu` is right everywhere. `<inttypes.h>` solves it with macros that expand to the right specifier for the platform:

```c
#include <inttypes.h>

uint32_t now = 123456;
printf("now = %" PRIu32 " ms\n", now);
```

`PRIu32` is a string (`"u"` on the VM, `"lu"` on AVR). C glues adjacent string literals together, so the format becomes `"now = %u ms\n"` or `"now = %lu ms\n"`, whichever is correct. There's `PRId16`, `PRIx32`, and so on for the other types. Small `uint8_t` and `uint16_t` values get promoted to `int` when passed to `printf`; the clean way to print them is `%u` with a cast: `printf("%u", (unsigned)a)`.

On the Uno you'll mostly use `Serial.print(x)`, which picks the format from the type for you (and `Serial.print(x, HEX)` for hex).

## Common beginner mistakes

- **Using `int` for `millis()` timestamps** (the bug above). Always `uint32_t` (or `unsigned long`).
- **Assuming `int` is 32 bits.** True on your VM, false on your Uno.
- **Reading a signed sensor register as unsigned** (or the reverse): −1 becomes 65535.
- **`uint8_t` loop counters**: `for (uint8_t i = 0; i < 300; i++)` never ends, because `i` wraps from 255 to 0 and is always less than 300.
- **Counting down with unsigned**: `for (unsigned i = 10; i >= 0; i--)` never ends either, because unsigned is always ≥ 0.
- **`%d` for a `long` or `%u` for a `uint32_t`**: works on one platform, prints garbage on the other. Use `%ld` and `PRIu32`.
- **Mixing signed and unsigned in a comparison**: `-1 < 1u` is **false**, because −1 is converted to unsigned (a huge number) first. When the values are variables (`int16_t offset` compared with `unsigned limit`), `-Wextra` warns (`-Wsign-compare`): one more reason to keep warnings on.
